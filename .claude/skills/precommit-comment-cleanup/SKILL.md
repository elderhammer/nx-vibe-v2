# 提交前注释体检（清理过期/无效注释）

## 何时用

- 准备 `git commit` 之前（已暂存或未暂存改动皆在）——把"改动使注释失实"的问题拦在提交前。
- 目标范围默认 = 全部未提交改动（staged + unstaged）；如需指定历史范围可带参，如 `git diff <ref>`。

## 红线

1. **只清理"与本次改动相关"的失实/无效注释**；本次改动范围之外的陈旧注释 → 记入提醒清单，不修改（外科手术原则）。
2. 注释改动不得改变任何代码行为；与注释同行的代码不动。
3. **拿不准 → 保留 + 提醒**，不删。
4. 一次只做注释清理：不顺手改格式/措辞/重构/无关代码。
5. 不自动 commit——清理完汇报，由用户复核 diff 后自行提交。

## 流程

### 1. 取改动清单

```bash
git status --porcelain   # 含未跟踪文件（??）
git diff HEAD            # 已暂存 + 未暂存
```

注意：未跟踪新文件不在 `git diff` 里——若是本次将提交的新代码文件（.cs 等），直接通读全文做注释评审。

### 2. 按文件逐 hunk 评审注释

对每个改动文件，检查 hunk 内及紧邻的注释（`//`、`/* */`、`///`、行尾注释；.md/.txt 内容不在默认范围，除非其中引用了本次改名/删除的文件或符号）。按类别定处理：

| 类别 | 典型形态（本仓库语境） | 处理 |
|---|---|---|
| A 失实描述 | 注释所述数值/参数/行为/顺序/命名与新代码矛盾（如 header 背景块声称"写直径被拒"而本 commit 已修复写路径） | 修正为新代码一致的说法，或删该句 |
| B 引用已消失实体 | 注释提及本次已删的变量/参数/常量/方法/序列阶段（s1~s5 式标签）/键名/文件 | 删该引用句；若整段注释只剩此类内容则删整段 |
| C 已完结的临时标注 | "待修复 / 候选 / 预期复现异常 / 未测写 / 消除候选 / 待观察"——本 commit 即对应修复或实证定案 | 改写为结论句或删除；只完结一部分的，改成仍为真的剩余断言 |
| D 复制错位 / 重复 | 与代码逐行复述、模板复制残留、上下文不符的粘贴注释 | 删 |
| E 外键编号漂移 | 引用"注册表 #N / 验收条目 I-x / issue / tool#N"等编号，其含义已随本 commit 变更 | 先核实编号现状，确证失实则修正；无法核实 → 保留 + 提醒 |

### 3. 连带检查（同文件、diff 之外）

本次改动**改名/删除**了某符号，同文件其它注释（方法头 doc、header 块）仍用旧名/旧语义描述它 → 一并修正。这是本次改动的直接后果，属清理范围。

### 4. 全局连带（只提醒，不直接改）

本次改动删除/改名的符号被**其它文件**的注释引用 → grep 出引用点，列提醒清单交用户决定——那可能是历史记录，别擅动。

### 5. 历史记录型注释的判别（本仓库大量 header 背景块）

"日期 + 背景 + 实证结论"的记录**不因后续提交而失实，默认保留**。只有当其中：
- 断言"当前代码如何"而现状已随本 commit 改变 → 修该句；
- 声称"修复未做 / 待做"而本 commit 已做 → 改为结论或删该句。

分不清是"记录"还是"状态断言" → 按记录对待，保留。

## 验证与汇报

1. 清理后重跑 `git diff HEAD` 复核：每条差异都属于注释清理，无行为改动混入。
2. 纯注释改动无需构建（注释不在编译面内）；如改动过程中误碰了代码行，diff 复核应能发现并回退。
3. 汇报清单，区分"已改"与"仅提醒"：

   `文件 | 位置(约行) | 类别(A–E/历史判别/其它) | 处理(改/删/保留-提醒)`

4. 提醒项与结论留给用户拍板后自行 commit。

## 注意

- 版权头 / 许可声明 / 自动生成标记一律不动。
- 注释掉的整段旧代码（disabled code）：默认不删，提醒用户。
- `git diff` 默认不含未跟踪文件——先查 `git status`。
- 遇冲突标记或格式混杂难以对照时，以改动后的当前文件内容为准。
